# 000 · Philosophy

## 为什么存在

AI agent 写码有三个老病。人在场时靠眼睛兜底，人不在场就裸奔：

| 老病 | 表现 | wfk 的机械约束 |
|---|---|---|
| 静默成功 | 说「已完成」，产物其实没变 / 变坏了 | 完成矩阵：每层 PASS 绑 `@提交 + tree + clean + cfg + wfk 版本`；缺层不能 merge |
| 边修边猜 | 越界乱改、顺手「优化」无关文件 | `write_scope` + `[forbidden]` + 改动面审计：越一个路径，gate exit 2 |
| 无法回溯 | 「上次怎么改的？为什么这么改？」 | 账本卡带决策记录 + 验证证据 + 成本；任何新会话 `wfk list` 即接手 |

大厂代码进主干要过 review + CI：review 拦人，CI 拦机器。agent 时代 review 拦不住（agent 不累也不烦），门禁成了唯一防线——每层都是可机械执行的断言；「摆回即红」（见 [001](001-workflow.md)）保证「绿了」真的等于「测到了」。

## 它怎么被验证

这套流程在 EarlyZ 排版引擎的量产战役（2026-11，Word 排版，判定器与引擎同源词表）里跑完一轮：

- 14 张 issue 连续 merged，每张过全链门禁，账本可回放；
- 排版正确率（双语料库可判项）：清洗集 579/579、留出集 388/388——双双 100%（此前 98.3%）；
- 摆回即红实战反复咬人：revert 后测试仍绿的「守卫无效」一律诚实拒绝，逼出真断言才放行。一例：某卡首跑 g1.5，revert 同步脚本后选中测试仍全绿——门禁判守卫无效，逼出对假仓真跑的五断言功能守卫，重跑 4 测试真红才放行；
- 工具本身经 19 个外部评审反例全数转拒绝（0.6.2 正确性修复），自测 125 条全绿。

## 设计约束

别加功能，除非第二个项目证明了必要。

- 状态用 markdown + TOML front-matter：可 diff、可 review、可 grep，人和 agent 都能读能改。
- 工具不含任何项目专有路径——项目差异全在 `workflow.toml`。
- 不内建 UI、不建服务、不碰网络：能一行命令说清的事不做平台。
- 改行为就要升版本：`wfk.py` 顶部 `__version__` 一改，历史证据自动失效——尺子变了，结论不能还算数。
